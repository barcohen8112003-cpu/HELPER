# פאנל שליטה מרחוק

כתובת HTTPS שאפשר לפתוח מכל דפדפן, להקליד בקשה ולקבל את התשובה של HELPER. ברירת המחדל היא קריאה בלבד. **שום דבר כאן לא פרוס ולא חשוף.** הפאנל כבוי עד `PANEL_ENABLED=on`.

## הנתיבים (ורק הם)

| Method | Path | צריך session? |
|---|---|---|
| `GET` | `/panel` | לא. עמוד סטטי אחד, זהה לכולם, בלי מידע אישי |
| `POST` | `/panel/api/login` | לא. ה-credential בגוף הבקשה, עם CSRF ו-Origin |
| `POST` | `/panel/api/logout` | כן |
| `GET` | `/panel/api/status` | כן |
| `POST` | `/panel/api/ask` | כן. `{ "text": "...", "id": "מזהה-ייחודי" }` |
| `GET` | `/panel/api/ask/<id>` | כן. התוצאה השמורה של אותה בקשה |
| `GET` | `/panel/api/catalog` | כן. פעולות המכשיר שה-credential מורשה להן, עם סכמת פרמטרים סגורה ומצב חיבור (חיבור בלבד, לא הוכחת ביצוע) |
| `POST` | `/panel/api/execute` | כן. `{ "id": "מזהה-ייחודי", "action": "lights:off", "params": { "room": "סלון" } }` → `202 {state:"running"}`. פעולה מהקטלוג בלבד, בלי מודל |
| `GET` | `/panel/api/execute/<id>` | כן. `running` (202), או `succeeded` / `failed` / `unknown` עם `detail` |

הפאנל מאזין על **פורט משלו** (`PANEL_PORT`, ברירת מחדל 3214, על `127.0.0.1`). על הפורט הזה כל נתיב אחר מחזיר 404. אתר ההגדרות, `/dash`, `/face` ו-`/bridge/*` נמצאים על 3210 ולא מוגשים כאן בכלל. כך גם proxy שמעביר יותר מדי לא מגיע לשום דבר מהם.

תשובות של `ask`: `200 {reply}`, `202 {state:"running"}` (בודקים אחר כך ב-`GET /panel/api/ask/<id>`), `200 {state:"unknown", note:"check audit"}`, `403` לא מורשה, `409` אותו id עם תוכן אחר, `429` עם `retryAfter`. בקשה שהתוצאה שלה לא ידועה **לא רצה שוב לבד**.

פעולות מכשיר מהפאנל רצות **רק** דרך `execute`. משפט כמו "תדליק את האורות" שנשלח ל-`ask` נדחה ולא מפעיל כלום. ב-`execute`, אורות דורשים `room` מרשימה סגורה, ו-`all` הוא בחירה מפורשת. `succeeded` אומר שהמכשיר דיווח על המצב המבוקש. `failed` אומר שבטוח ששום דבר לא נשלח (הרשאה, ולידציה, מכשיר תפוס, אין התאמה) או שהמכשיר עצמו דיווח על כישלון. `unknown` אומר שהפקודה אולי יצאה ואין אישור: היא לא רצה שוב לבד, וקודם בודקים את מצב המכשיר. כל מכשיר מחזיק נעילה אחת שמשותפת לפאנל, לפקודות המהירות בוואטסאפ ולכלים של המודל. כשמכשיר תפוס, התשובה היא `failed` עם `reason: "busy"`.

**`status` הוא מצב חיבור בלבד.** `pcBridgeConnected: true` אומר שהגשר למחשב בבית מחובר. הוא **לא** אומר שפעולה על הטלוויזיה, הטלפון או Webtop תצליח. אל תבטיח פעולה על סמך הסטטוס.

## הרשאות

- credential חדש מקבל `status` ו-`ask:read` בלבד: שאלות כלליות וכלים ציבוריים (חיפוש, חדשות, מזג אוויר, לוח עברי, מטבע, צבע אדום, תחבורה). אין זיכרון, צ'אטים, מייל, יומן, קבצים, צילומי מסך, מחשב, טלפון או הגדרות.
- השער יושב בנקודת הדיספצ'ר של הכלים (`src/agent.js` runCall) ובודק כל קריאה, גם לכלי שלא הוצע למודל. כל מה שלא ברשימה נחסם.
- ההקשר מבודד: המודל לא רואה את היסטוריית הוואטסאפ, את הסיכום או את הזיכרון, אלא רק את השיחה הקודמת של אותו credential.
- פעולות מכשיר (אורות הדלקה/כיבוי, כיבוי טלוויזיה) כבויות. כל אחת היא מתג נפרד באתר ההגדרות, והן רצות רק דרך הפקודות המהירות המדויקות. כלי המכשירים של המודל חסומים לפאנל תמיד.
- אישורים הולכים לוואטסאפ בלבד. «כן» מהפאנל לא מאשר כלום. בזמן שבקשה מחכה, הפאנל מציג «מחכה לאישור בוואטסאפ».

## הנפקה וביטול

אתר ההגדרות → **פאנל מרחוק**: «צור» מנפיק credential, והקוד המלא מוצג פעם אחת. בשרת נשמר רק SHA-256 שלו (`data/panel.json`). «בטל» מנתק מיד את כל ה-sessions שלו, בלי לגעת באפליקציה, בדיסקורד או ב-credentials אחרים. שם גם המתגים של המכשירים והמגבלות: בקשות לשעה (30), בדיקות מצב לשעה (120), ניסיונות כניסה לדקה לכל כתובת (10), ותקרה יומית לכל הפאנל (200). בהגעה לתקרה נשלחת התראה אחת לוואטסאפ.

## דוגמת curl (credential רק בכותרת, אף פעם לא בכתובת)

```sh
# בלי credential: 403
curl -i https://panel.example.com/panel/api/status

# עם credential: 200
curl -i -H "Authorization: Bearer $HELPER_PANEL_CREDENTIAL" https://panel.example.com/panel/api/status

# בקשה, עם id שלך. אם החיבור נפל, בודקים לפי אותו id ולא שולחים שוב
curl -s -H "Authorization: Bearer $HELPER_PANEL_CREDENTIAL" -H "Content-Type: application/json" \
  -d '{"text":"מה מזג האוויר בתל אביב?","id":"req-20261108-0001"}' https://panel.example.com/panel/api/ask
curl -s -H "Authorization: Bearer $HELPER_PANEL_CREDENTIAL" https://panel.example.com/panel/api/ask/req-20261108-0001
```

## חשיפה (רק אחרי אישור)

ההמלצה לשרת בענן: **Caddy על השרת** מול פורט הפאנל, עם דומיין. Caddy מנפיק ומחדש תעודת Let's Encrypt לבד, בחינם. אם אין דומיין, אפשר תת-דומיין חינמי של DuckDNS שמצביע על כתובת השרת.

1. `.env` בשרת: `PANEL_ENABLED=on` ו-`PANEL_PUBLIC_ORIGIN=https://panel.example.com` (הכתובת המדויקת, בלי `/` בסוף).
2. `docker compose -f docker-compose.yml -f deploy/panel/docker-compose.panel.yml up -d --build`. הפורט מתפרסם רק על `127.0.0.1` של השרת. כל עוד `PANEL_ENABLED=on` כתוב ב-`.env`, העדכון האוטומטי (`scripts/auto-update.sh`) מוסיף את הקובץ הזה בעצמו, כך שעדכון לא סוגר את הפאנל.
3. `PANEL_DOMAIN=panel.example.com caddy run --config deploy/panel/Caddyfile`. ה-Caddyfile מעביר רק את תשעת הנתיבים, לפי method ו-path, ומחזיר 404 לכל השאר.
4. פתיחת 80 ו-443 בחומת האש של השרת (Caddy צריך את 80 לאימות התעודה).

Tailscale Funnel הוא חלופה חינמית בלי דומיין, אבל הוא מסנן רק לפי path ולא לפי method. הוא בטוח יותר כאן רק בזכות הפורט הנפרד, ולכן הוא לא ההמלצה הראשונה.

**בעיה קיימת שכדאי לתקן בנפרד:** `docker-compose.yml` מפרסם את 3210 (אתר ההגדרות ו-`/bridge/*`) לכל הרשת ב-HTTP גלוי, וגם `UI_PUBLIC_HOST` נבנה כ-`http://`. הפאנל לא משכפל את זה.
